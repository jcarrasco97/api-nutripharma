Misión: Ayudarme a desarrollar y escalar "NutriPharma", una plataforma SaaS B2B / ERP para la gestión clínica, logística y financiera de una red de nutricionistas y farmacias.

A continuación, te detallo el contexto absoluto del proyecto. Debes basar todas tus respuestas, arquitecturas y código en estas reglas:

1. STACK TECNOLÓGICO Y VERSIONES

Frontend: React (SPA), Vite, Tailwind CSS v4.

UI Kit: Componentes propios basados en Radix UI y Shadcn, extraídos a shared/components/ui/. El diseño no usa plugins antiguos de animaciones de Tailwind; usamos inyecciones de @keyframes nativas en @layer utilities de index.css (conocido internamente como "La Vacuna Global" para animar los [data-state="open"]).

Backend: Java 25, Spring Boot 4.0, PostgreSQL/MySQL.

Seguridad y Auditoría: Spring Security (JWT, Stateless), Hibernate Envers (Trazabilidad Inmutable), Interceptores HTTP para logs de IPs y User-Agents.

Almacenamiento: API de Google Drive para almacenamiento de evidencias y facturas.

2. ARQUITECTURA FRONTEND (Domain-Driven Modular / Feature-Based Architecture)
El frontend espejo del backend. Está prohibido el código espagueti. La estructura divide la app en módulos estancos:

/core o shared/: Elementos genéricos (UI, Utils, Hooks genéricos).

/modules/: Dominios de negocio aislados (auth/security, operations, organization, sales, documents). Cada módulo tiene sus propios components, hooks, services y pages, y expone lo necesario mediante un index.js.

El renderizado de listas complejas siempre usa programación defensiva (?.map, || []) para evitar bloqueos (White Screen of Death).

3. ROLES Y CONTROL DE ACCESO (RBAC)

ROLE_ADMIN (Gestor/Paco): Modo Dios de negocio. Gestiona la empresa, aprueba pedidos, da de alta usuarios, audita evidencias y liquida pagos.

ROLE_NUTRICIONISTA (Clínico): Pasa consultas, adjunta evidencias, sube facturas de gastos/kilometraje y genera carritos de compra.

ROLE_FARMACIA (Punto de venta): Ve su saldo virtual generado por comisiones y realiza pedidos.

ROLE_SUPERADMIN (Soporte/Nacho): Cuenta técnica "Break-Glass" para mantenimiento; invisible para el negocio.

Nota de Arquitectura: Un administrador que también pasa consulta tiene DOS cuentas separadas (Identity Segregation). No hay modales de cambio de rol dinámico.

4. REGLAS DE NEGOCIO CRÍTICAS

Máquina de Estados de Consultas: BORRADOR (editable, foto mutable) -> CONFIRMADA -> VALIDADA (foto bloqueada criptográficamente) -> LIQUIDADA. Si hay un error: CON_INCIDENCIA.

Finanzas Exactas: Prohibido usar Float/Double en Backend; uso exclusivo de BigDecimal.

E-commerce (Doble Cesta): Los pedidos combinan productos pagados con Dinero Real, Saldo Virtual (comisiones) y Bonificados (gratis). Se exige un umbral de 80€ en Dinero Real para procesar una liquidación.

Comisiones Multicapa: Un pedido en una farmacia puede repartir su comisión entre varias nutricionistas (sumando siempre el 100%).

El Gatekeeper: El Administrador es un cuello de botella intencionado. Debe revisar el desglose en el "Centro de Validaciones" antes de aprobar un pedido o liquidar una consulta.

5. BASES DE DATOS Y TRAZABILIDAD (Single Source of Truth)

Prohibido el Hard Delete: Se usa Soft Delete (activo = false con @SQLDelete). Para cumplir el RGPD (Derecho al olvido), el backend anonimiza datos personales pero conserva el ID y la integridad financiera.

Duplicados: La validación de IDs únicos (Email, Referencia) se captura en la Capa de Servicio (lanzando IllegalArgumentException), no se deja colapsar a la base de datos (evitando errores 500 ciegos).
